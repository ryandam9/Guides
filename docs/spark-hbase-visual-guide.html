01 / SPARK

Who runs a Spark application?

Start with the Spark processes. A process is a program that runs. An application can start more than one job.

01 / Application

Application

One user program that Spark runs. It has one driver and its own executors.

02 / Process

Driver

The driver plans jobs. It schedules tasks. It collects task results and reports job status.

03 / API

SparkSession

The main entry point for DataFrame and SQL work. In PySpark, its usual name is spark.

04 / API

SparkContext

The lower-level entry point to Spark. SparkSession gives access to it.

05 / Service

Cluster Manager

A service that gives cluster resources to applications. Examples are YARN and Kubernetes.

06 / Machine

Worker Node

A machine that runs application work. A node can host executor processes.

07 / Process

Executor

A process that runs tasks. It also keeps cached data and shuffle data.

08 / Resource

Core / Task Slot

An allocated executor CPU core normally lets one CPU task run at a time.

09 / Setting

Deploy Mode

Client mode starts the driver at the submit location. Cluster mode starts it in the cluster.

Client mode

The driver starts where the user submits the program. The executors run on cluster nodes.

Cluster mode

The cluster starts the driver. This is useful for an unattended daily report.

Do not confuse these terms: An application is not one job. One application can run many jobs. An executor is not a RegionServer.

The driver can show the Spark version and the application ID. Your cluster version can differ from the reference version.

print("Application ID:", spark.sparkContext.applicationId)
print("Default parallelism:", spark.sparkContext.defaultParallelism)
print("Spark UI:", spark.sparkContext.uiWebUrl)

On EMR: how YARN gives resources to Spark

On Amazon EMR, the cluster manager is YARN. YARN controls the memory and the CPUs of the cluster nodes. Spark does not own the nodes. Spark must ask YARN for space before it starts a process. If YARN has no free space, your application waits.

10 / YARN service

ResourceManager

The YARN service that controls the cluster. It knows the free memory and vCPUs of each node. It keeps the queues and decides which application gets space next. On EMR, it runs on the primary node. Its web UI uses port 8088.

11 / YARN service

NodeManager

The YARN agent on each core node and task node. It tells the ResourceManager how much memory and how many vCPUs the node gives to YARN. It starts containers and monitors their memory.

12 / Resource

Container

A fixed quantity of memory and vCPUs on one node, for example 4 GiB and 2 vCPUs on node B. Each process of your application runs in one container. A container cannot use two nodes.

13 / Process

ApplicationMaster

The first container that YARN starts for an application. Each application has its own ApplicationMaster (AM). The AM asks the ResourceManager for more containers, for example 10 executors of 6 GiB each.

14 / Setting

Queue

A share of the cluster resources. The scheduler puts each application in a queue. On EMR, the scheduler is usually the Capacity Scheduler. If the queue is full, the application waits.

15 / Resource

Memory Overhead

Memory that an executor uses outside the JVM heap. The container size is spark.executor.memory plus spark.executor.memoryOverhead. The default overhead is 10% of the executor memory, with a minimum of 384 MiB.

Node capacity: Two settings tell YARN how much each node gives: yarn.nodemanager.resource.memory-mb and yarn.nodemanager.resource.cpu-vcores. EMR sets them from the instance type. The operating system and the HDFS and YARN services use the remaining memory.

Client mode

The driver runs in the spark-submit process, on the node where you submit the application. The ApplicationMaster is small (spark.yarn.am.memory, 512 MiB by default). It only asks for executor containers. If the spark-submit process stops, the application stops. Use client mode for notebooks and the PySpark shell.

Cluster mode

The driver runs in the ApplicationMaster container, on a cluster node. The size of this container comes from spark.driver.memory and its overhead. The application continues if you close your terminal. Use cluster mode for scheduled jobs.

What lives in the driver and what goes to the executors

The SparkSession and its SparkContext are only in the driver. Each application has one SparkContext. Spark does not copy it to the executors. The deploy mode only changes the location of the driver. In client mode, the SparkContext is in the spark-submit process, usually on the EMR primary node. In cluster mode, it is in the ApplicationMaster container. In the two modes, the executors run in other containers and do not have a SparkContext.

Only in the driver

The SparkSession and the SparkContext. The connection to YARN. The query plans, the DAG of stages, and the task scheduler. The results of collect().

Sent to the executors

Serialized tasks. Each task has your function, the variables that the function uses, and one partition to process. Broadcast variables, one copy for each executor. The Spark configuration and the files from --jars and --py-files, when the executor starts.

Do not use the SparkContext in a function that runs on the executors: The SparkContext cannot be serialized. If a map function or a UDF uses spark or sc, the job fails. Spark shows an error that says that the SparkContext can only be used on the driver. Do the Spark operation in the driver, or use a join or a broadcast variable.
The application stays in ACCEPTED

YARN has no free space for the ApplicationMaster container. Open the YARN UI on port 8088. Look at the queue of the application and at the memory that other applications use.

Fewer executors than you asked for

The cluster has no free space for more containers. Spark runs tasks on the executors that it has. EMR turns on dynamic allocation by default, so Spark asks for executors when the work needs them.

Container killed by YARN

A container used more physical memory than its size, and the NodeManager stopped it. The log shows "Container killed by YARN for exceeding memory limits". The exit code is usually 143 (SIGTERM). Increase spark.executor.memoryOverhead or decrease the memory that each task uses.

Exit code 137

Code 137 is SIGKILL. The process did not stop after SIGTERM, or the Linux out-of-memory killer stopped it. Examine the memory of the node and of the container.

02 / SPARK

What data does Spark process?

A DataFrame has rows and columns. A schema defines the column types. Spark can read data from many systems.

Version: all local PySpark examples in this chapter use APIs available in Spark 3.5.0.

01 / Data type

DataFrame

A distributed table with named columns and a schema. Use it for most PySpark data work.

02 / Data type

Schema

The names and data types of the columns. A schema tells Spark how to interpret each value.

03 / Structure

Row / Column

One row contains one record. A column contains one field for all rows.

04 / API

RDD

A Resilient Distributed Dataset. It is a lower-level distributed collection with partitions.

05 / API

Dataset

A typed distributed collection in Scala and Java. Python uses the DataFrame API.

06 / API

Spark SQL

An interface to write SQL statements for structured data. It uses the Spark SQL engine.

07 / Metadata

Catalog / Table

A catalog holds table information. A table name can refer to data in files or another source.

08 / Extension

UDF

A user-defined function. Use native Spark functions first when they can do the work.

09 / Input

Data Source

The system or format from which Spark reads data. Examples are Parquet, CSV, JDBC, and an HBase connector.

03 / SPARK

How does Spark plan work?

The query plan is not the same as the Python statement list. Spark can combine operations and select a better execution plan.

01 / Operation

Transformation

An operation that defines a new dataset. Examples are filter, select, and groupBy.

02 / Operation

Action

An operation that requests a result or writes output. Examples are count, show, and write.save.

03 / Rule

Lazy Evaluation

Spark records many transformations before it runs the necessary work. An action can start execution.

04 / Plan

DAG

A directed acyclic graph. It shows how computation steps depend on one another.

05 / Recovery

Lineage

The recorded operations from which Spark can calculate a dataset again.

06 / Plan

Logical Plan

The operations that the query must do. Spark can optimise this plan.

07 / Plan

Physical Plan

The execution steps that Spark selects. Use explain() to inspect them.

08 / Optimiser

Catalyst

The Spark SQL optimiser. It rewrites and selects query plans.

09 / Optimisation

Predicate Pushdown

A data source applies a supported filter before it sends the data to Spark. Support depends on the source.

EXAMPLE · PYSPARK LAZY TRANSFORMATIONS + ACTIONSpark ≥ 3.5
from pyspark.sql import functions as F

# Use payments_df from Chapter 02. These lines build a plan.
report = (payments_df
    .filter(F.col("status") == "SUCCESS")
    .groupBy("merchant")
    .agg(F.sum("amount_aud").alias("total_aud")))

report.explain("formatted")  # Inspect the physical plan.
report.orderBy("merchant").show()  # Request the result.

Look for an Exchange operator in the physical plan. It usually indicates a redistribution of records.

PYSPARK · COMPARE A NARROW STEP AND A WIDE STEPSpark ≥ 3.5
# The filter usually has a narrow dependency.
narrow = payments_df.filter(F.col("status") == "SUCCESS")

# This grouping generally needs a shuffle (wide dependency).
wide = narrow.groupBy("merchant").agg(
    F.count("*").alias("payment_count"))

wide.explain("formatted")  # Look for Exchange in the plan.
wide.orderBy("merchant").show()
04 / EXECUTION

How Spark divides the work

Spark processes partitions in parallel. The Spark driver plans the work. Spark executors run the tasks.

Concept 01

Job

A job is a computation. An action can start a job.

Concept 02

Stage

A stage is a set of tasks. A shuffle usually makes a new stage.

Concept 03

Task

A task is one unit of work. An executor runs each task.

Concept 04

Partition

A partition is one part of a dataset. One task processes one partition in a stage.

EXAMPLE · PYSPARK JOB TRIGGERSpark ≥ 3.5
# Define work with the sample DataFrame.
result = (payments_df
    .filter("amount_aud > 100")
    .groupBy("merchant")
    .count())

# The action requests the result and can start Spark jobs.
result.show()

This lower-level RDD example helps you see the relationship between a partition and a task. The four partitions do not represent HBase regions.

PYSPARK · SHOW THE ROWS IN EACH RDD PARTITIONSpark ≥ 3.5
# RDD example: four partitions contain the integers 0 to 11.
sc = spark.sparkContext
numbers = sc.parallelize(range(12), 4)

# Each mapPartitionsWithIndex call runs for one RDD partition.
def inspect_partition(index, values):
    yield (index, list(values))

print(sorted(numbers.mapPartitionsWithIndex(inspect_partition).collect()))
Spark does not run a transformation immediately. It starts the necessary work when an action needs a result. One action can start more than one job.
05 / SPARK

How do partitions and shuffles work?

Spark uses partitions to divide data. A stage starts one task for each partition that the stage must process.

Version: Spark 3.5.0+. Adaptive Query Execution can change the final shuffle partition count. DataFrame.rdd needs classic Spark.

01 / Dependency

Narrow Dependency

A child partition needs data from a limited number of parent partitions. A filter is usually narrow.

02 / Dependency

Wide Dependency

A child partition can need data from many parent partitions. groupBy often needs a wide dependency.

03 / Data move

Shuffle

Spark redistributes records among partitions. A shuffle often moves data across the network.

04 / Operation

Repartition

An operation that makes a new partition layout. It normally causes a shuffle.

05 / Operation

Coalesce

An operation that merges partitions to reduce the partition count. It does not do a full shuffle, and it cannot increase the count.

06 / Capacity

Parallelism

The number of tasks that can do work at the same time. Task count and available cores both matter.

07 / Recovery

Task Attempt

One execution attempt for a task. Spark can retry a failed task.

08 / Placement

Data Locality

How close the task is to its input data. Local reads can reduce data transfer.

09 / Problem

Skew

An uneven distribution of data or work. One large partition can delay a stage.

EXAMPLE · PYSPARK PARTITION COMMANDSSpark ≥ 3.5
# Use the sample payments_df from Chapter 02.
print("Current partitions:", payments_df.rdd.getNumPartitions())

# Repartition normally introduces a shuffle.
eight = payments_df.repartition(8)
print("After repartition:", eight.rdd.getNumPartitions())

# Coalesce can reduce the count without a full shuffle.
four = eight.coalesce(4)
print("After coalesce:", four.rdd.getNumPartitions())

# The SQL shuffle partition target is a session setting (default 200).
# Examples that change it reset it at the end with spark.conf.unset().
print("Shuffle target:", spark.conf.get("spark.sql.shuffle.partitions"))

Find the partition that Spark assigns to each row. The result depends on Spark’s hash partitioning.

PYSPARK · SEE THE PARTITION ID OF EACH RECORDSpark ≥ 3.5
# These four Spark partitions are NOT the four HBase regions.
distributed = (payments_df
    .repartition(4, "merchant")
    .withColumn("spark_pid", F.spark_partition_id()))

distributed.select("merchant", "row_key", "spark_pid").show()
(distributed.groupBy("spark_pid").count()
    .orderBy("spark_pid").show())

With AQE disabled, the configured value is easier to see in the planned shuffle. AQE can change the count at runtime.

PYSPARK · CHANGE THE SHUFFLE PARTITION TARGETSpark ≥ 3.5
spark.conf.set("spark.sql.adaptive.enabled", "false")
spark.conf.set("spark.sql.shuffle.partitions", "2")
merchant_totals = (payments_df
    .groupBy("merchant")

06 / SPARK

How do joins and aggregations work?

A query can combine two datasets. A group operation can calculate a total for each key. These operations often need data movement.

Version: broadcast(), joins, and AQE settings in these examples are available in Spark 3.5.0.

01 / Operation

Join

An operation that combines records with a condition, such as merchant_id.

02 / Strategy

Broadcast Join

Spark sends one small input to executor processes. The large input does not need a join-key shuffle in this plan.

03 / Strategy

Sort-Merge Join

Spark can shuffle and sort both inputs by the join key, then match the rows.

04 / Operation

Aggregation

An operation that calculates a group result. Examples are sum, count, and avg.

05 / Optimisation

Partial Aggregation

Spark calculates local group results before it combines them. This can reduce shuffle data.

06 / Optimisation

AQE

Adaptive Query Execution. Spark can change some plan decisions with runtime statistics.

07 / Optimisation

Column Pruning

Spark reads only the columns that the query needs, when the source supports it.

08 / Optimisation

Partition Pruning

Spark skips storage partitions that do not match a supported filter.

09 / Metadata

Statistics

Data such as row counts and sizes. The optimiser can use these values to select a plan.

EXAMPLE · COMPLETE PYSPARK BROADCAST JOINSpark ≥ 3.5
from pyspark.sql import functions as F

# The lookup has only three rows, so a broadcast join can fit.
merchant_lookup = spark.createDataFrame([
    ("Grocery", "Retail"), ("Travel", "Services"),
    ("Energy", "Utilities")
], ["merchant", "sector"])

joined = (payments_df
    .join(F.broadcast(merchant_lookup), on="merchant", how="left")
    .filter(F.col("status") == "SUCCESS"))
report = (joined.groupBy("sector")
    .agg(F.sum("amount_aud").alias("total_aud")))
report.explain("formatted")
report.orderBy("sector").show()

AQE can combine small shuffle partitions. The exact final plan depends on runtime statistics and your Spark settings.

PYSPARK · ENABLE ADAPTIVE QUERY EXECUTIONSpark ≥ 3.5
# These settings apply to subsequent query planning.
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
spark.conf.set("spark.sql.shuffle.partitions", "8")

# AQE can change parts of the plan while a job runs.
adaptive_totals = (payments_df.groupBy("merchant")
    .agg(F.sum("amount_aud").alias("total_aud")))
adaptive_totals.collect()  # Finish the small demonstration.
adaptive_totals.explain("formatted")

# Restore the default shuffle target for later examples.
spark.conf.unset("spark.sql.shuffle.partitions")

Filter early

Keep SUCCESS records before an expensive join when the result permits it. Check whether the source pushes the filter down.

Use AQE

AQE can merge small shuffle partitions, optimise supported skewed joins, or change a join strategy.

Do not assume: A broadcast hint is always accepted. The join type and the physical plan determine the final strategy.
07 / SPARK

How does Spark use memory and recover?

Spark can keep reused data in memory or on disk. Spark can calculate lost partitions again when it has the necessary lineage and input.

01 / Reuse

Cache

Keep reusable dataset data so later actions can read it more quickly.

02 / Reuse

Persist

Store reusable data with a selected storage level. Data can use memory, disk, or both.

03 / Cleanup

Unpersist

Remove a cached or persisted dataset when you do not need it.

04 / Memory

Spill

Write intermediate data to disk when there is not enough memory for an operation.

05 / Recovery

Checkpoint

Save a stable copy to reliable storage. Spark can then use it as a new start point.

06 / Recovery

Fault Tolerance

The ability to continue or recover after some failures. Spark can retry tasks and recompute lost partitions.

07 / Sharing

Broadcast Variable

A read-only value that Spark sends efficiently to executors for reuse in tasks.

08 / Sharing

Accumulator

A variable that tasks can add to. The driver can read its aggregated value.

09 / Memory

Garbage Collection

A JVM memory cleanup operation. High GC time can indicate memory pressure.

EXAMPLE · PYSPARK CACHE AND CLEANUPSpark ≥ 3.5
from pyspark.sql import functions as F

# The Chapter 02 dataset includes payment_date.
successful = payments_df.filter(F.col("status") == "SUCCESS").cache()
successful.count()  # Materialise the cache on this action.
by_merchant = successful.groupBy("merchant").count()
by_day = successful.groupBy("payment_date").count()
by_merchant.show()
by_day.show()
successful.unpersist()  # Release the stored partitions.

MEMORY_AND_DISK lets Spark store cached partitions on disk when needed. Use storage only when reuse justifies the cost.

PYSPARK · SELECT A PERSISTENCE LEVELSpark ≥ 3.5
from pyspark import StorageLevel

reusable = (payments_df
    .filter(F.col("status") == "SUCCESS")
    .persist(StorageLevel.MEMORY_AND_DISK))
try:
    reusable.count()  # Populate the storage level.
    reusable.groupBy("merchant").count().show()
finally:
    reusable.unpersist()
Production checks: Do not cache every DataFrame. Do not use collect() to move a large dataset to the driver. If a task spills or fails with an out-of-memory error, inspect partition sizes and memory metrics.
08 / SPARK

How does Spark read and write files?

Spark can read S3 files, HDFS files, SQL sources, and connector data. The source type can change how Spark plans input partitions.

01 / Format

Parquet

A column-based file format. It is useful for many analytic workloads.

02 / Format

CSV / JSON

Text-based file formats. They are easy to exchange, but Spark often needs more work to parse them.

03 / Read

File Scan

A read operation that gets records from files. Spark can combine small files or divide some large inputs.

04 / Layout

Storage Partition

A folder or table layout made with keys such as dt=2026-10-03.

05 / Output

Write Mode

The instruction that tells Spark what to do with output that already exists, such as append or overwrite. Check the scope before you overwrite data.

06 / Performance

Small-File Problem

A large number of very small files can increase the time to list files and schedule tasks.

    F.col("payment_date") == F.to_date(F.lit("2026-10-03")))
(daily.groupBy("merchant").count()
    .write.mode("overwrite").parquet(output_dir))
print("Report written to:", output_dir)

# Production alternative: read a partitioned Parquet location on S3A.
# daily = spark.read.parquet("s3a://YOUR-BUCKET/payments/") \
#     .filter(F.col("dt") == "2026-10-03")

In this example, a table partition is an output folder. It is not a Spark execution partition or an HBase region.

PYSPARK · PARTITION AN OUTPUT BY PAYMENT DATESpark ≥ 3.5
# Spark 3.5.0+; partitionBy() creates file-system folders.
from pathlib import Path
from tempfile import mkdtemp
from pyspark.sql import functions as F

output = str(Path(mkdtemp(prefix="spark-partition-demo-"))
             / "payments_partitioned")
(payments_df
    .withColumn("dt", F.date_format("payment_date", "yyyy-MM-dd"))
    .write.mode("overwrite").partitionBy("dt").parquet(output))

# This reads storage partitions. It does not read HBase regions.

# Production alternative: output = "s3a://YOUR-BUCKET/payments_partitioned/"

What changes when data arrives continuously?

A batch job reads bounded data. A streaming query processes new input as it arrives.

Version: these rate-source and micro-batch examples work with Structured Streaming in Spark 3.5.0+.

01 / Mode

Batch

A computation on a bounded input. A daily report is a batch job.

02 / Mode

Structured Streaming

A Spark API that processes new data with DataFrame operations.

03 / Execution

Micro-Batch

One small batch of newly available input data. Structured Streaming uses this model by default.

04 / Control

Trigger

A setting that controls when the query checks for new work.

05 / Time

Event Time

The time at which an event occurred. It can differ from arrival time.

06 / Time

Watermark

A limit that helps Spark manage late events and state for supported stateful operations.

07 / State

State Store

Concept 06

HBase divides a region into two daughter regions when the split policy selects a split.

SCENARIO 01DRIVER MEMORY

Do not send a large dataset to the driver

Situation. An audit has two million payment rows. The result must be the total amount for each merchant.

✕ Bad way AVOID

PYSPARK · LESS EFFICIENTSpark ≥ 3.5
# Sends every row to the driver. Avoid for large input.
totals = {}
for row in payments_df.collect():
    if row.status == "SUCCESS":
        key = row.merchant
        totals[key] = totals.get(key, 0) + row.amount_aud
print(totals)

Problem. collect() transfers all payment rows to the driver. The driver then does the aggregation. A large result can exhaust driver memory.

✓ Better way PREFER WHEN SUITABLE

PYSPARK · BETTER APPROACHSpark ≥ 3.5
# Compute the totals on the executors.
totals = (payments_df
    .filter(F.col("status") == "SUCCESS")
    .groupBy("merchant")
    .agg(F.sum("amount_aud").alias("total_aud")))
totals.show()  # Only a small summary is displayed.

Why it helps. Spark filters rows and calculates partial totals in parallel. It transfers only the small final report to show().

Check in the Spark UI: Watch the driver heap and the SQL aggregation nodes. Compare the amount of data returned to the driver.

Important: collect() is valid when you know that the final result is small. The eight-row sample dataset will not show a meaningful speed difference.

✕ Bad way AVOID

SCENARIO 03SHUFFLE

Do not group all raw values when Spark can aggregate them

Situation. A settlement report must calculate the sum of successful payments for each merchant.

✕ Bad way AVOID

PYSPARK · LESS EFFICIENTSpark ≥ 3.5
# RDD groupByKey keeps the individual values in groups.
from decimal import Decimal
pairs = (payments_df.filter("status = 'SUCCESS'").rdd
    .map(lambda row: (row["merchant"], row["amount_aud"])))
slow = (pairs.groupByKey()
    .mapValues(lambda values: sum(values, Decimal("0.00"))))
print(slow.collect())  # Small sample result only.

Problem. groupByKey() moves many individual values and holds groups. This can increase shuffle data and memory pressure.

✓ Better way PREFER WHEN SUITABLE

PYSPARK · BETTER APPROACHSpark ≥ 3.5
# DataFrame aggregation supports partial aggregation.
fast = (payments_df
    .filter(F.col("status") == "SUCCESS")
    .groupBy("merchant")
    .agg(F.sum("amount_aud").alias("total_aud")))
fast.show()

Why it helps. Spark SQL can calculate partial totals before the shuffle. The network then carries fewer intermediate values.

Check in the Spark UI: Compare shuffle write bytes, spill, and the HashAggregate nodes in the SQL plan.

Important: This recommendation is for an aggregate such as SUM. Some algorithms must keep every value. Do not replace them with SUM.

SCENARIO 04JOIN

Broadcast a genuinely small lookup table

Situation. The large payment table needs a three-row merchant-to-sector lookup table.

✕ Bad way AVOID

SCENARIO 07CACHE

Persist a costly dataset only when you reuse it

Situation. Three separate reports use the same expensive filtered input from S3 or HBase.

✕ Bad way AVOID

PYSPARK · LESS EFFICIENTSpark ≥ 3.5
# Each independent action can start another upstream read.
filtered = payments_df.filter("status = 'SUCCESS'")
filtered.count()
filtered.groupBy("merchant").count().show()
filtered.agg(F.sum("amount_aud")).show()

Problem. The three actions can repeat an expensive input scan and filter.

✓ Better way PREFER WHEN SUITABLE

PYSPARK · BETTER APPROACHSpark ≥ 3.5
from pyspark import StorageLevel
filtered = (payments_df.filter("status = 'SUCCESS'")
    .persist(StorageLevel.MEMORY_AND_DISK))
try:
    filtered.count()  # Populate the cache.
    filtered.groupBy("merchant").count().show()
    filtered.agg(F.sum("amount_aud")).show()
finally:
    filtered.unpersist()

Why it helps. Spark can reuse the persisted filtered records. The first action fills the cache and later actions can read it.

Check in the Spark UI: Check the Storage tab, input scan count, and query plan for InMemoryTableScan.

Important: A cache adds memory pressure and a population cost. Do not cache data that you use once. Test the benefit with the real workload.

SCENARIO 09SMALL FILES

Group rows by the output folder before a partitioned write

Situation. A report writes SUCCESS and FAILED rows into separate status= folders. The DataFrame arrives from an earlier step with many partitions.

✕ Bad way AVOID

✓ Better way PREFER WHEN SUITABLE

Important: The extra shuffle is the cost. It pays off when it removes many small files. For small files that already exist, plan a separate compaction.

# the MERGE hints force the shuffle join that a large table would get.
skewed = (payments_df.hint("MERGE")
    .join(merchant_lookup.hint("MERGE"), on="merchant"))
skewed.explain("formatted")  # SortMergeJoin, Exchange on merchant

Problem. The join shuffles by merchant, so every row of the hot merchant goes to one task. That task controls the stage completion time.

✓ Better way PREFER WHEN SUITABLE

PYSPARK · BETTER APPROACHSpark ≥ 3.5
# Spark 3.5.0+. First check AQE: it splits skewed join partitions.
print(spark.conf.get("spark.sql.adaptive.skewJoin.enabled"))  # 'true'

# If the measured skew remains, salt the hot side and copy the other.
N = 8
pay_salted = payments_df.withColumn(
    "salt", F.pmod(F.xxhash64("row_key"), F.lit(N)))
lookup_salted = merchant_lookup.crossJoin(
    spark.range(N).withColumnRenamed("id", "salt"))
balanced = (pay_salted.hint("MERGE")
    .join(lookup_salted.hint("MERGE"), on=["merchant", "salt"])
    .drop("salt"))
balanced.explain("formatted")

Why it helps. The salt spreads the hot merchant's rows over up to 8 join tasks. The code copies each merchant row on the other side 8 times, so every salted payment still finds its match.

Check in the Spark UI: Compare maximum and median task duration and shuffle read in the join stage. Confirm that one key causes the slow task.

Important: Do not salt a sum or count. Spark already adds partial sums inside each task before the shuffle, so a hot key sends only one small row per task. A salt suits joins and aggregations that keep every value, such as collect_list.

SCENARIO 11AQE

Do not use one shuffle partition for a large report

Situation. A cluster has many free CPU slots, but one reduce task must process the full shuffle.

✕ Bad way AVOID

PYSPARK · LESS EFFICIENTSpark ≥ 3.5
# A leftover override forces one reducer.
spark.conf.set("spark.sql.adaptive.enabled", "false")
spark.conf.set("spark.sql.shuffle.partitions", "1")
slow = payments_df.groupBy("merchant").count()
slow.explain("formatted")  # Exchange hashpartitioning(..., 1)

# Remove the overrides again (the better way shows why that is the fix).
spark.conf.unset("spark.sql.shuffle.partitions")
spark.conf.unset("spark.sql.adaptive.enabled")

Problem. One reducer can become a bottleneck. Other executor slots remain unused during the reduce stage.

✓ Better way PREFER WHEN SUITABLE

PYSPARK · BETTER APPROACHSpark ≥ 3.5
# Remove the overrides. The Spark 3.5 defaults already do the right
# thing: 200 initial shuffle partitions, then AQE merges small ones.
spark.conf.unset("spark.sql.shuffle.partitions")   # default 200
spark.conf.unset("spark.sql.adaptive.enabled")     # default true
print(spark.conf.get("spark.sql.adaptive.coalescePartitions.enabled"))
fast = payments_df.groupBy("merchant").count()
fast.explain("formatted")  # AdaptiveSparkPlan

Why it helps. The fix is to delete the override, not to add settings. With the defaults, Spark starts with enough shuffle partitions, and AQE merges the small ones at runtime. For very large shuffles, tune spark.sql.adaptive.advisoryPartitionSizeInBytes instead of the partition count.

Check in the Spark UI: Look for AdaptiveSparkPlan, shuffle partition size, coalesced partitions, active tasks, and spill.

Important: Look for overrides in spark-defaults.conf, job submit flags and notebook setup cells. The final number of reducers can be lower than 200 under AQE. The eight-row sample will not benefit from this change.

SCENARIO 12MANY ACTIONS

Replace a loop of count actions with one aggregation

Situation. A developer wants the row count for each merchant on a large source.

✕ Bad way AVOID

PYSPARK · LESS EFFICIENTSpark ≥ 3.5
# Three independent count actions.
for name in ["Grocery", "Travel", "Energy"]:
    n = payments_df.filter(
        F.col("merchant") == name).count()
    print(name, n)

Problem. Each loop iteration starts a Spark action and can scan the source again.

✓ Better way PREFER WHEN SUITABLE

PYSPARK · BETTER APPROACHSpark ≥ 3.5
# One distributed aggregation for the same three merchants.
counts = (payments_df
    .filter(F.col("merchant").isin(
        "Grocery", "Travel", "Energy"))
    .groupBy("merchant")
    .agg(F.count("*").alias("payment_count")))
counts.orderBy("merchant").show()

Why it helps. One groupBy counts all three merchants in one query.

Check in the Spark UI: Compare the number of Spark jobs, repeated file scans, and total source input bytes.

Important: A merchant with no rows appears as zero in the loop but is absent from the grouped output. Add a lookup and a left join if you need groups with zero values.

SCENARIO 13HBASE

Limit an HBase scan before HBase sends records

Situation. A settlement job needs one row-key range, but the HBase table contains years of payment history.

✕ Bad way AVOID

PYSPARK · LESS EFFICIENTSpark ≥ 3.5
# Spark 3.5.0+.
# The shared setup defines hbase_df = payments_df for an OFFLINE demo.
# On the real cluster, replace it with a genuine connector scan.
full_report = (hbase_df.groupBy("merchant")
    .agg(F.sum("amount_aud").alias("total_aud")))
full_report.show()
# An unrestricted real HBase scan can read unrelated row-key ranges.

Problem. A full region scan can transfer many irrelevant rows. A later Spark filter cannot undo the HBase read cost.

✓ Better way PREFER WHEN SUITABLE

PYSPARK · CLUSTER SKETCH, NOT RUN OFFLINESpark ≥ 3.5
# Sketch for the Apache hbase-connectors Spark data source.
# Needs the hbase-spark jar and hbase-site.xml on the cluster.
from functools import reduce
hbase_df = (spark.read.format("org.apache.hadoop.hbase.spark")
    .option("hbase.table", "payments")
    .option("hbase.columns.mapping",
            "row_key STRING :key, merchant STRING d:merchant, "
            "amount_aud STRING d:amount_aud, status STRING d:status")
    .option("hbase.spark.use.hbasecontext", False)
    .load())

# One bounded range per salt bucket (00# to 03#). This connector turns
# comparisons on the :key column into scan start and stop rows.
ranges = [(f"{b:02d}#TXN1001", f"{b:02d}#TXN1005") for b in range(4)]
in_range = reduce(lambda x, y: x | y, [
    (F.col("row_key") >= lo) & (F.col("row_key") < hi) for lo, hi in ranges])
selected = (hbase_df.filter(in_range)
    .select("row_key", "merchant",
            F.col("amount_aud").cast("decimal(12,2)").alias("amount_aud")))
selected.explain("formatted")

Why it helps. Each RegionServer reads only the rows between the start and stop keys of each bucket, and only the mapped columns. With TableInputFormat, set the same bounds with hbase.mapreduce.scan.row.start and hbase.mapreduce.scan.row.stop (one range per job).

Check in the Spark UI: Inspect actual HBase scan settings, RegionServer scan/RPC metrics, and connector-reported pushed filters. Do not rely on a DataFrame filter alone.

Important: There is no universal PySpark HBase connector API, and option names change between connectors and versions. Check how yours turns filters into scan ranges. The key ranges here are illustrative; a date-range report needs the date in the row key after the salt, such as salt#yyyymmdd#txn.

SCENARIO 14GLOBAL SORT

Do not sort a large dataset without a business need

Situation. A pipeline writes an intermediate Parquet dataset. Consumers do not need a global row order.

✕ Bad way AVOID

PYSPARK · LESS EFFICIENTSpark ≥ 3.5
# Spark 3.5.0+. This global order adds work that files may not need.
out = str(Path(mkdtemp(prefix="spark-global-sort-")) / "result")
(payments_df.orderBy(F.col("amount_aud"))
    .write.mode("overwrite").parquet(out))

Problem. A global order can introduce a range shuffle and extra sort work. Parquet readers do not need this order for ordinary intermediate steps.

✓ Better way PREFER WHEN SUITABLE

PYSPARK · BETTER APPROACHSpark ≥ 3.5
# Spark 3.5.0+. Write without a global sort.
out = str(Path(mkdtemp(prefix="spark-no-global-sort-")) / "result")
(payments_df.write.mode("overwrite").parquet(out))
# Sort a small final result only when the report needs a rank.
report = payments_df.groupBy("merchant").agg(
    F.sum("amount_aud").alias("total_aud"))
report.orderBy(F.desc("total_aud")).show()

Why it helps. The intermediate write avoids an unnecessary sort. You can still sort the small final report for display.

Check in the Spark UI: Compare Sort and Exchange operators, shuffle bytes, and sort spill in the SQL plan.

Important: Keep the global sort when downstream business logic needs ordered rows. Parquet files do not guarantee a global output order for later readers.
